# Stage 1.5 — Real-Time Streaming, Recorder & Replay

**Date:** 2026-04-03
**Status:** Active
**Stage:** 1.5 of 7 (between read-only MVP and paper trading)
**Depends on:** Stage 1 (v0.1.0-readonly) — COMPLETE

## Objective

Build a robust, observable real-time data pipeline that can:
- Stream live orderbook updates from Polymarket WebSocket
- Maintain stable connections with heartbeat and reconnect
- Persist all frames to JSONL for offline analysis
- Replay recorded sessions deterministically
- Expose connection health in the terminal dashboard

This is NOT paper trading. This is proving the transport layer is reliable
enough to build paper trading on top of.

## Success criteria

The stage is complete when:
1. A session can run for 10+ minutes receiving continuous WS frames
2. Connection drops are detected and reconnected automatically
3. Resubscription happens after reconnect (no silent data loss)
4. All frames are recorded to JSONL with timestamps
5. A recorded session can be replayed from disk
6. Dashboard shows live frame count, latency, and connection state
7. Clean shutdown preserves all recorded data
8. Logs capture connection lifecycle events (connect, disconnect, reconnect, subscribe)

## Non-goals

- Paper trading or simulated execution
- Strategy logic or signal generation
- Multi-market correlation or analysis
- Performance optimization (throughput, batching)

## Acceptance criteria (detailed)

### 1. Stable WebSocket connection
- [ ] Connect to `wss://ws-subscriptions-clob.polymarket.com/ws/market`
- [ ] Subscribe using decimal token IDs in `assets_ids` with `initial_dump: true`
- [ ] Send text `"PING"` every 30s (Polymarket keepalive, not WS ping frame)
- [ ] Detect stale connection if no message received within 60s
- [ ] Log connection state transitions: connecting → connected → reconnecting → disconnected

### 2. Real frames received and persisted
- [ ] Parse `book`, `price_change`, `last_trade_price` event types
- [ ] Record each frame as a `DomainEvent` with timestamp, source, sessionId
- [ ] JSONL file contains: session_meta, subscription events, data frames, session_end
- [ ] No data loss on normal operation (all frames that arrive get recorded)

### 3. Reconnect and resubscribe
- [ ] On connection drop: exponential backoff reconnect (1s → 2s → 4s → ... → 30s cap)
- [ ] After reconnect: automatically resubscribe to the same assets
- [ ] Log reconnect attempts with attempt number and delay
- [ ] Record a `reconnect` event in JSONL

### 4. Replay usable
- [ ] CLI command or script to replay a recorded JSONL session
- [ ] Replay prints frames in order with original timestamps
- [ ] Replay can filter by event type (book, price_change, etc.)
- [ ] Replay validates session integrity (meta → events → end)

### 5. Shutdown clean
- [ ] SIGINT/SIGTERM triggers graceful WS disconnect (close code 1000)
- [ ] Recorder flushes all buffered data before exit
- [ ] Session end event recorded with frame count and duration
- [ ] Exit code 0

### 6. Logs/health visible in terminal
- [ ] Dashboard shows: WS state, frames received count, last frame timestamp, latency
- [ ] Dashboard shows: markets subscribed, reconnect count
- [ ] Health check includes WS frame recency (healthy if frame < 60s ago)

## Risk register

| Risk | Impact | Mitigation |
|------|--------|------------|
| WS disconnects frequently | High | Exponential backoff, reconnect counter, alerts |
| Silent data loss (frames dropped) | High | Frame counter, gap detection, JSONL integrity checks |
| JSONL grows too large | Medium | File rotation, size limits (existing maxFileSizeMb) |
| Polymarket changes WS protocol | Medium | Record raw frames, version subscription format |
| Keepalive timing wrong | Low | Configurable interval, monitor PONG responses |

## Protocol reference

From Stage 1 validation and protocol research:

```
Subscription:
  {"assets_ids": ["<decimal_token_id>", ...], "type": "market", "initial_dump": true}

Keepalive:
  Send: "PING" (text, every 30s)
  Receive: "PONG" (text)

Event types:
  book           — full orderbook snapshot (bids, asks, timestamp, hash)
  price_change   — incremental order update (asset_id, price, size, side)
  last_trade_price — trade execution (price, size, side, fee_rate_bps)
  tick_size_change — price granularity change
  best_bid_ask   — requires custom_feature_enabled: true
```
